# Internal provenance & transport trust

No secret ever travels on internal traffic. Trust is **proof-of-possession**:
keys are derived locally from the vault on both sides, so a request either
carries a valid cryptographic proof or it does not — and there is nothing
reusable to sniff, copy, or replay.

The threat model is a live unauthorized process inside the VLAN with network
reachability. Cleartext secrets or identity headers would be fatal: one
sniffed request would hand the attacker reusable material. That class of
failure is removed by construction.

## The two transports

| Transport | Proof | Mechanism |
|---|---|---|
| **HTTP** (request/reply) | per-service HMAC signature | canonical string over method+path+timestamp+nonce+body-hash, verified at the receiving edge |
| **NATS** (events/jobs/durability) | sealed envelope | message keys derived from the same vault; a valid envelope can only be produced by a key holder |

Both key families derive from the vault with **label separation** — a key
derived for HTTP signing can never be confused with a message key, and keys
are **per-service**: the signature tells you *which* service signed, not just
that *some* fleet member did.

## HTTP signing — `auth/http-signing.ts`

`signInternalRequest` / `verifyInternalRequest` implement the canonical
scheme:

- `x-pb-service` — the signer service-code (per-service attribution)
- `x-pb-keygen` — the vault generation the key was derived from
- `x-pb-timestamp` — rejected outside `SIGNATURE_SKEW_MS`
- `x-pb-nonce` — single-use, replay protection
- `x-pb-signature` — HMAC over the canonical string
- `x-pb-sealed` — AES-GCM blob carrying the sensitive identity headers

**Identity never travels in cleartext.** `x-user-*` headers (and the
configured auth header names) are classified sensitive by
`isSensitiveInternalHeader`, removed from the cleartext header set, sealed
into the blob, and re-injected only at the receiving edge after verification.
A request that smuggles extra cleartext `x-user-*` headers alongside a valid
signature has them stripped before the sealed identity is merged — the
sealed blob is the only identity source.

## Replay protection — `auth/nonce-cache.ts`

`isNonceReplay` uses Redis `SET NX PX` over the existing cache port, with an
in-memory fallback, and **fails closed**: when neither backend is available
the nonce counts as replayed. Nonce checking applies to write methods
(POST/PUT/PATCH/DELETE) — a replayed read is inert by construction, so GET
requests skip the roundtrip.

## Outbound — `http/internal-client.ts`

`internalFetch(url, init)` signs every internal call automatically:
sensitive headers are extracted, sealed, and the signature headers are
emitted on the wire. Every BE→US and US→US HTTP hop — the proxy, OpenAPI
discovery, docs-pack pulls, map-key-schemas — funnels through it, so correct
signing is a construction property, not a discipline. `resetInternalClient`
exists for tests.

## Inbound — the edge

`verifyEdgeRequest` (`auth/edge-verification.ts`) is the receiving half:
buffers the exact body bytes, verifies the signature over method+path+body,
opens the sealed blob, strips any cleartext sensitive headers, and re-injects
the verified identity for downstream handlers.

`createHttpServer` wires it through the `internalProvenance` option:

- `"enforce"` — every request except `/health` and declared
  `identityExemptPaths` (webhook ingress) must carry a valid signature.
  **The microservice default.**
- `"verify-if-present"` — signature verified when present, unsigned traffic
  tolerated (mixed-use edges).
- `"off"` — library default, no verification.

Because verification happens before routing and the body is re-injected,
downstream handlers are unchanged: they read identity headers exactly as
before, but those headers are now *proven*.

The BE serves public browser traffic on a custom express server, so
enforcement there is per-route: `requireInternalProvenance()` mounts the
same verification on endpoints that exist for service-to-service traffic
only (e.g. the docs-pack pull).

## NATS — sealed envelopes and service lanes

Envelope sealing is validated at the transport layer before any route logic
runs: a message on a governed subject can only exist if the publisher holds
vault-derived message keys. Routes that exist for service-to-service traffic
declare it explicitly:

```ts
import { serviceLaneVerify } from "@primebrick/sdk";

{
  subject: "service.register",
  permissions: [],
  verify: serviceLaneVerify, // no user context exists — the envelope is the proof
  handler: async ({ request }) => { /* … */ },
}
```

Without the explicit lane declaration the default chain resolves a user
context and rejects service traffic with `AUTH_USER_CONTEXT_MISSING`.

## Rotation continuity

Vault keys rotate hourly. Signatures carry `x-pb-keygen`, and verification
accepts keys from generations still inside the retention window — a request
signed just before a rotation verifies fine in-flight, and dies only after
the generation is trimmed. There is no handshake, no enrollment, no key
distribution: rotation is a non-event for running services.

## The User-Agent is observability, never trust

Outbound calls still stamp `User-Agent: name/version (capabilities) runtime`
— it is valuable log and trace metadata (which version is calling). It is
never consulted for any trust decision: the cryptographic provenance headers
are the identity, the UA is a label.

## Who does what

| Side | Code | Duty |
|---|---|---|
| **Vault** | `secret-vault.ts` | root key material, hourly rotation, generation retention |
| **Publisher** (any service) | `internalFetch` + `signInternalRequest` | derive per-service key locally, sign + seal every outbound call |
| **US edge** | `createHttpServer` with `internalProvenance: "enforce"` | verify signature, open sealed identity, strip cleartext smuggling |
| **BE edge** | `requireInternalProvenance()` per-route | same verification on service-to-service endpoints of the public server |
| **NATS lanes** | `serviceLaneVerify` | explicit service-to-service declaration; the envelope is the proof |
