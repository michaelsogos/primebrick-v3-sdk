# Ext-JSON

Ext-JSON is the standard JSON serialization layer for Primebrick — the
**only sanctioned codec** across BE, microservices, DAL, SDK, UI and FE.
The canonical implementation lives in `@primebrick/core` (`src/ext-json.ts`)
and the SDK re-exports it, so there is exactly one codec in the workspace.
Raw `JSON.stringify` / `JSON.parse` and argument-less `response.json()`
reads are banned by the `ext-json` check-standards rule (`NO_EXEMPT` —
legitimate plain-JSON boundaries, e.g. external REST specs or signed
artifacts, declare themselves via `.devin/check-standards.json` `allowPaths`).

## Why Ext-JSON exists

Standard `JSON.stringify()` throws on `bigint`:

```ts
JSON.stringify({ id: 42n });
// TypeError: Do not know how to serialize a BigInt
```

Primebrick uses native `bigint` for all integer IDs (UUIDs are strings, but
numeric IDs, timestamps, and counters are `bigint`). Ext-JSON makes the types
predictable across the wire format:

| JSON value | Wire format | Parsed TS type |
|------------|-------------|----------------|
| `42n` (bigint) | `42` | `bigint` |
| `42` (small int) | `42` | `bigint` (reviver forces it) |
| `3.14` (float) | `3.14` | `number` |
| `1e5` (scientific) | `100000` | `bigint` (integer) |
| `"alice"` (string) | `"alice"` | `string` |
| `true` (boolean) | `true` | `boolean` |
| `null` | `null` | `null` |

The rule is simple: **every integer is `bigint`, every float is `number`**.
No `number | bigint` ambiguity — the type is determined by whether the value
has a decimal point, not by its magnitude.

## The strict codec

`extJsonParse` is a strict three-stage parse, not a plain `JSON.parse`:

1. **Validate** — a scanner enforces the grammar strictly and rejects what
   native parse silently accepts: duplicate keys (never last-wins), trailing
   commas, malformed input.
2. **Materialize** — native `JSON.parse` builds the object graph.
3. **Restore** — a source-order flag walk converts every integer-valued
   number to `bigint`, exactly — including values above 2^53 that plain
   `JSON.parse` would corrupt and `BigNumber`-based codecs used to degrade
   to imprecise `number` at 21+ digits.

`extJsonStringify` emits `bigint` values as JSON numbers (via `JSON.rawJSON`
where supported, with a `json-bigint` fallback on older engines).

## Usage

### Direct functions

```ts
import { extJsonStringify, extJsonParse } from "@primebrick/sdk";

const data = { entity_id: 42n, price: 3.14, name: "widget" };
const json = extJsonStringify(data);
// → '{"entity_id":42,"price":3.14,"name":"widget"}'

const parsed = extJsonParse<{ entity_id: bigint; price: number; name: string }>(json);
// parsed.entity_id → 42n (bigint)
// parsed.price → 3.14 (number)
```

### Round-trip type preservation

The round-trip preserves types exactly — `bigint` in, `bigint` out; `number`
in, `number` out. This is what makes the SDK's NATS™ and HTTP layers safe for
DAL rows that mix `bigint` IDs with `number` floats:

```ts
const original = {
  id: 42n,              // bigint  → bigint
  count: 7,             // number (integer) → bigint (reviver forces it)
  price: 3.14,          // number (float)   → number
  name: "widget",       // string → string
  active: true,         // boolean → boolean
  nested: { qty: 100n },// bigint nested → bigint
};

const roundTrip = extJsonParse<typeof original>(extJsonStringify(original));
// typeof roundTrip.id       → "bigint"
// typeof roundTrip.count    → "bigint"   (was a number, now bigint — by design)
// typeof roundTrip.price    → "number"
// typeof roundTrip.name     → "string"
// typeof roundTrip.nested.qty → "bigint"
```

The one asymmetry to know about: a plain `number` integer on the sender
becomes `bigint` on the receiver. This is intentional — it makes every
integer `bigint` everywhere, so consumers never write `number | bigint` union
types. If you send a `number` integer, expect a `bigint` back.

### Express middleware (BE)

```ts
import { extJsonMiddleware, extJsonBodyParser } from "@primebrick/sdk";

// Parse request bodies with BigInt-safe JSON (replaces express.json())
app.use(extJsonBodyParser());

// Serialize responses with Ext-JSON
app.use(extJsonMiddleware());
// res.json() now uses Ext-JSON serialization for all subsequent responses
```

The middleware replaces `res.json()` with Ext-JSON serialization. The body
parser replaces `express.json()` with BigInt-safe parsing so that large
integer values in request bodies (e.g. `bigint` config values) are parsed
as native `bigint` instead of losing precision through `JSON.parse`. Install
both once before any routes.

### NATS™ (microservices)

`NatsClient.publish()`, `subscribe()`, and `subscribeRequest()` use Ext-JSON
internally. Microservice code never calls `extJsonStringify` / `extJsonParse`
directly — just pass plain objects and receive plain objects.

## Sub-path import

If you need only the JSON functions without pulling in NATS™/auth code paths:

```ts
import { extJsonStringify, extJsonParse, extJsonMiddleware, extJsonBodyParser } from "@primebrick/sdk/json";
```

## The frontend

The FE uses the **same canonical codec** — `@primebrick/ui` re-exports
`@primebrick/core`'s `extJsonParse` / `extJsonStringify`, and
`src/lib/api-ext.ts` wraps `apiFetch` with `apiFetchExt` for wire reads.
One codec, everywhere: wire bodies, storage payloads, editors, previews,
smart inputs, fixtures and tests all use Ext-JSON.
