# Database migrations

`migrations/apply-patches.ts` applies SQL patch files with **content-hash
immutability**. It is DB-agnostic — it speaks to a `DatabasePort` adapter,
never to a driver directly.

## How a patch is applied

Files are read from `patchesDir` in **filename-sorted order** and each is
checked against the registry table
`public.primebrick_database_patches` (patch_id + content_sha256):

| Situation | Behavior |
|---|---|
| same patch_id, same SHA | **skip** — already applied |
| same patch_id, different SHA | **fail** — an applied patch was modified in place (immutable by design) |
| patch_id absent, same SHA recorded | **register without re-executing** — the body was applied by a different filename |
| otherwise | `BEGIN` → run SQL → `INSERT` registry row → `COMMIT` |

Returns `{ appliedOrRegistered, skipped }`. A missing or empty directory
is a no-op, not an error.

## The rules that make it safe

- **Never edit an applied patch.** The sha mismatch fails loudly instead
  of silently drifting — to change a shipped patch, ship a *new* one.
- **Filename = patch id** (`patchIdFromFilename`) — ordering and identity
  come from the name, so use the timestamp prefix helpers:
  `utcTimestampForFilename()`, `slugifyPatchSegment()`.
- **Each patch is transactional** — a failure rolls back its own
  statements but leaves earlier patches committed (they're idempotent,
  re-running is safe).

## Fire-and-forget patches

Alongside `db-meta/patches/` (the ordered, registered kind), services use
`db-meta/fire-and-forget/` for one-off operational SQL (seeds, backfills,
fix-ups applied manually per environment). They are **not** tracked in the
registry — idempotency is the author's responsibility; write them so a
second execution is harmless (`INSERT ... ON CONFLICT`, `IF EXISTS`,
existence guards).

## Usage

```ts
import { applyPatches } from "@primebrick/sdk";

const result = await applyPatches(
  join(process.cwd(), "db-meta", "patches"),
  myDatabasePortAdapter,   // wraps the consumer's driver
);
// → { appliedOrRegistered: 3, skipped: 12 }
```

Each service wires this into its `pnpm db:migrate` script with its own
schema's adapter (see `scripts/database-patch-apply.ts` in any US).
